# D1 MuJoCo Protocol Simulator

This package runs the calibrated D1 URDF and grasping scene in MuJoCo and
emulates the D1 arm's native Cyclone DDS service.

## Current contract

- subscribes to `rt/arm_Command` using
  `unitree_arm::msg::dds_::ArmString_`;
- publishes `current_servo_angle` using
  `unitree_arm::msg::dds_::PubServoInfo_`;
- publishes JSON ACK, joint and status messages on `rt/arm_Feedback`;
- supports function codes 1, 2, 4, 5, 6 and 7;
- converts SDK arm degrees to MuJoCo radians;
- converts SDK gripper angle `[-30, 60] deg` to `Joint6 [0, 0.03] m`;
- applies a configurable 10 Hz command limit, 8.97 Hz feedback and target
  smoothing;
- intentionally sends execution ACK before physical convergence, matching the
  measured reason clients must use joint feedback.

## Run

From the repository root:

```bash
source /home/tony/miniconda3/etc/profile.d/conda.sh
conda activate trash_collection
export PYTHONNOUSERSITE=1
pip install -e ./d1_mujoco_sim
d1-mujoco-sim
```

Show the actual primitive collision proxies:

```bash
d1-mujoco-sim --show-collisions
```

Tune an arm pose directly with the MuJoCo `Control` sliders:

```bash
d1-mujoco-sim --manual-control --show-collisions
```

Manual-control mode leaves `data.ctrl` under viewer ownership and rejects DDS
motion commands, so the sliders are not overwritten by the protocol control
loop. `Joint0_position` through `Joint5_position` are radians;
`Joint6_position` is gripper travel in metres.

Start manual tuning from an exact six-joint pose (the quotes are required by
the shell):

```bash
d1-mujoco-sim --manual-control \
  --initial-arm-pose '[0, -1.54, 1.55, 0, -0.6, 0]'
```

Contact points and contact forces remain available as separate toggles in the
MuJoCo `Rendering` panel; they are not enabled automatically because the
default markers are intentionally large. The colors identify proxy roles:
cyan for the base and main arm, orange for
elbow/wrist bodies, and magenta for the two finger contact bodies. The proxies
remain physically active but are fully transparent during a normal launch.
The viewer starts from an overview orbit pose but remains freely rotatable,
pannable and zoomable.

The finger proxies use a provisional sliding-friction coefficient of `5.0` to
represent the rubber pads fitted to the physical gripper. This remains a
sim2real calibration parameter rather than a material datasheet value.

## Object scene

The simulator imports the textured OBJ/PBR assets under the repository's
`objects/` directory for the yellow cube, bowl and zucchini. The visual meshes
use RGB, metallic, roughness and normal maps; contact uses lightweight dynamic
proxies instead of the 50,000-face render meshes:

- yellow cube: 50 mm box;
- zucchini: 150 mm ellipsoid whose centre slice matches the measured
  40.0 mm by 33.1 mm mesh cross-section;
- bowl: bottom disc plus a 12-segment hollow wall.

The base centre is `(x=0, y=0)` on the midpoint of the near 0.8 m edge. The
white spawn boundary is `x=[0, 0.6] m`, `y=[-0.4, 0.4] m`, with base `+x`
pointing inward. Seed `0` is configured by default. Placements account for the
object footprint, base clearance and inter-object clearance.

The ground uses the perspective-corrected real-floor photograph generated by
`tools/prepare_ground_texture.py`. The photographed calibration square is
provisionally configured as 0.6 m per side in `sim.yaml`; update that value
after measuring the real square. The white spawn boundary is a separate
visual-only geometry slightly above the floor, so the texture cannot hide it.
The distant background is a neutral grey-blue procedural skybox; it affects
only rendering, while the existing scene lights remain responsible for
illumination.

For the simulation-only MoveIt grasp baseline, object world poses are emitted
at 25 Hz on UDP loopback port `15002`. This channel never carries arm commands
and is deliberately separate from the D1-compatible DDS interface; it will be
replaced by camera perception above the manipulation layer.

Override the deterministic placement seed with:

```bash
d1-mujoco-sim --seed 1
```

Viewer geometry groups are: environment/outline `0`, arm STL `1`, object
visuals `2`, arm collision `3`, and object collision `4`.

## ROS 2 scene visualization

`--ros-scene` publishes two independent RViz `MarkerArray` layers at 25 Hz:

- `/d1_mujoco/object_meshes`: the original textured object OBJ files at the
  live MuJoCo free-body poses;
- `/d1_mujoco/physical_collisions`: every active MuJoCo contact geom,
  including the arm, gripper, objects and ground.

The collision markers are generated from the compiled runtime model rather
than a second geometry configuration. The finite RViz ground marker represents
the configured rendering patch of MuJoCo's physically infinite plane.

## RealSense D435i

The camera attached to `Link6` contains two independent fixed MuJoCo cameras:

- `d435i_color`: calibrated RGB, `1280x720`, `fx=899.023`, `fy=898.874`;
- `d435i_depth`: factory depth, `848x480`, `fx=fy=430.400`.

Their retained optical sites are `wrist_camera_color_optical_frame` and
`wrist_camera_depth_optical_frame`. Both use the RealSense optical convention (`+X`
right, `+Y` down, `+Z` forward). The Link6-to-color pose comes from the
hand-eye calibration in `config/sim.yaml`; the depth pose is composed with the
factory depth-to-color transform read from physical camera serial
`250122077729`.

The camera visual is a decimated export of `D435i_Official_CAD` from the
supplied `D1-550.blend`, baked into the RGB optical frame. The orange
`main_stand` mount is exported separately in `LYH_D1_FRAME_Link6`; it does not
inherit the measured RGB pose. This deliberately keeps the designed mount
relationship and calibrated camera relationship independent, so a mismatch
is visible. Both are visual-only and do not alter arm collision or grasp
physics. In the MuJoCo viewer, select
`d435i_color` or `d435i_depth` in the camera selector to inspect the on-arm
view, then return to the free camera for orbit controls.

MuJoCo's native camera is an ideal pinhole camera. When ROS publication is
enabled, the bridge applies the measured RGB `plumb_bob` distortion as a
post-process and converts metric renderer depth to RealSense-compatible
`16UC1` units. The native MuJoCo viewer itself remains pinhole-rendered.

The stable ROS topic layout identifies this eye-in-hand device by role:

- `/wrist_camera/color/image_raw` (`rgb8`);
- `/wrist_camera/color/camera_info`;
- `/wrist_camera/depth/image_rect_raw` (`16UC1`, millimetres);
- `/wrist_camera/depth/camera_info`;
- `/wrist_camera/aligned_depth_to_color/image_raw` (`16UC1`, RGB grid);
- `/wrist_camera/aligned_depth_to_color/camera_info`.

`--camera-debug` additionally publishes the visualization-only topics
`/wrist_camera/debug/depth_plasma` and
`/wrist_camera/debug/aligned_depth_plasma`. Depth-to-color alignment uses the
measured stream extrinsics and intrinsics, fills the RGB pixel grid, preserves
zero for missing samples, and keeps the nearest Z16 value where projections
overlap.

Static TF publishes `Link6 -> wrist_camera_link`, with separate children
`wrist_camera_color_optical_frame` and
`wrist_camera_depth_optical_frame`. Start the simulator and docked RViz image
panels without running the grasp demo with one command from the workspace root:

```bash
./view_mujoco_camera.zsh
./view_mujoco_camera.zsh --headless  # RViz only, without the MuJoCo GUI
```

For the complete fixed-cube grasp acceptance, use the unified entry point.
`--headless` independently disables the MuJoCo viewer, while `--rviz` enables
RViz with the robot, object meshes, optional MuJoCo/MoveIt collision layers,
RGB, aligned-depth plasma and optional raw-depth plasma panels:

```bash
./accept_cube_grasp.zsh
./accept_cube_grasp.zsh --headless
./accept_cube_grasp.zsh --rviz
./accept_cube_grasp.zsh --headless --rviz
```

RViz defaults to `RobotModel` and `Object Meshes` enabled, with `MuJoCo
Physical Collisions` and `MoveIt Planning Collisions` disabled. Both collision
layers are top-level displays and can be toggled independently. Their ground
markers are opaque whenever their layer is enabled. In an interactive terminal,
`--rviz` waits for Enter before starting the grasp and waits again after a
successful grasp, leaving both the initial and final states available for
inspection. Non-interactive invocations skip both waits.

Camera publication is scheduled at up to 10 Hz. Point-cloud publication is
deliberately left for a later perception step. Rendering, registration and ROS
serialization run in a latest-frame-only worker so camera load cannot block
the 1 kHz physics/control loop. A deterministic alignment
acceptance triptych can be regenerated with:

```bash
MUJOCO_GL=egl conda run -n trash_collection \
  python d1_mujoco_sim/tools/generate_alignment_preview.py
```

For a terminal-only smoke test:

```bash
d1-mujoco-sim --headless --duration 5
```

The physics loop remains at a fixed 1 kHz while viewer synchronization is
downsampled to 60 Hz. Rendering therefore cannot throttle simulation time by
forcing a GUI synchronization on every physics step.

Official SDK clients can use the same commands, topic names and generated DDS
types. The only intentional default difference is DDS domain `42`, rather than
the hardware default `0`, to prevent an accidentally connected physical arm
from receiving test commands. Set `ChannelFactory::Init(42)` in simulation
clients, or explicitly change `dds.domain_id` only when the network is known
to be safe.

## Test

```bash
cd d1_mujoco_sim
pytest
```

`tests/dds_cpp_probe.cpp` is an end-to-end compatibility probe built against
the official generated C++ DDS types. It deliberately uses domain 42.

One way to build it from the repository root is:

```bash
g++ -std=c++17 -O2 \
  d1_mujoco_sim/tests/dds_cpp_probe.cpp \
  D1_SDK/src/msg/ArmString_.cpp D1_SDK/src/msg/PubServoInfo_.cpp \
  -I D1_SDK/src/msg -I /usr/local/include/ddscxx \
  -I /usr/local/include/iceoryx/v2.0.2 -L /usr/local/lib \
  -lunitree_sdk2 -lddsc -lddscxx -lrt -lpthread \
  -o /tmp/d1_dds_cpp_probe
```

## Deliberate limitations

- The empirical smoothing constants are initial tunable values, not identified
  parameters from the physical arm.
- Single-joint `delay_ms` is validated but not yet fitted to a measured motion
  profile.
- Vendor mesh collision remains disabled because the nominal URDF contains
  assembly overlap. Measured primitive proxies provide stable arm, wrist and
  finger collision; table, object and bin geometry are the next scene layer.
- `power=0` is acknowledged but does nothing, matching the measured firmware;
  this is not an emergency stop.
- No bin has been added yet.
- Aligned depth-to-color and point-cloud topics are not implemented yet.
