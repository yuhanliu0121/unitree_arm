## 0. 当前实现状态（优先于下文的早期规划描述）

当前工作区已经实现并验证：

- `d1_mujoco_sim`：D1 SDK 协议兼容的 MuJoCo 服务，DDS domain 42；
- `d1_ros2_control`：隔离 SDK ABI 的 UDP gateway、hardware interface，以及
  `joint_state_broadcaster`、`arm_controller`、`gripper_controller`；
- `d1_moveit_config`：SRDF、KDL IK、OMPL、控制器映射和规划专用简化碰撞体；
- `d1_grasp_demo`：读取 seed-0 方块仿真真值，执行“预抓取—垂直下降—
  双侧接触检查—闭合—垂直抬升—保持验证”。
- eye-in-hand D435i：官方 CAD 和 `main_stand` 支架可视模型、RGB/Depth 独立光学 frame、真机
  内参、实测 Link6→RGB 外参和本机 factory Depth→RGB 外参均已进入
  MuJoCo；固定相机名为 `d435i_color`、`d435i_depth`。

2026-08-10 的端到端验收结果：

- TCP 与方块中心对齐误差小于 1 mm；
- 闭合后左右手指均有接触，法向力约为 7.50 N / 7.50 N；
- TCP 规划抬升 0.10 m，保持 12 秒期间物理方块稳定在初始位置上方
  0.097 m，没有继续下滑；
- `pick_cube` 正常输出 `GRASP SUCCEEDED` 并以 0 退出；
- `d1_mujoco_sim` 共 34 项 pytest 全部通过。

重要边界：MoveIt 使用启动时生成的 primitive collision URDF；共享 vendor
URDF 保留 STL，以免破坏 MuJoCo 导入时的 link-frame 变换。为避免在已知
不代表真机能力的仿真打滑上继续耗时，当前任务级仿真明确采用强稳定参数：
夹爪 `kp/kv=800/80`、闭合目标越过物理下限 5 mm、指垫滑动摩擦系数
`5.0`、指垫—物体接触时间常数 2 ms，以及物体线性/角阻尼 `2.0/4.0`。
这些只用于稳定验证规划和抓取流程，不能直接视为真机参数；
双指 mimic equality 同样采用 2 ms 高刚度约束，避免单侧接触载荷造成开合
不对称。
此外启用 MuJoCo 椭圆摩擦锥、`impratio=10` 和 2 次 NoSlip 迭代，以消除
软接触模型在接触力充足时仍会产生的慢速摩擦漂移。这仍是正常接触求解，
没有焊接、附着或强制跟随物体。
真机前仍须根据 D1 实测力/电流重新拟合动力学参数。

仿真相机 ROS 2 感知桥已经实现，目标发布频率配置为 10 Hz：发布与 RealSense 官方
驱动同语义的 RGB `rgb8`、原始 Depth `16UC1`、对齐到 RGB 的 Depth
`16UC1`、三份 `CameraInfo` 和静态 TF。机械臂相机统一使用
`/wrist_camera` namespace 及 `wrist_camera_*` frames，以便与未来 Go2
机身相机区分。RGB 图会应用实测 `plumb_bob` 畸变；
原始 `16UC1` 深度有效范围固定为 0.20—10.0 m，范围外发布为零；彩色
调试图固定把 0.20—2.0 m 映射到 plasma 色带，范围外显示为黑色。
Plasma 话题位于 `/wrist_camera/debug`，仅在 `--camera-debug` 下发布；
相机渲染、对齐和 ROS 序列化使用 latest-only 后台线程，物理/控制循环只复制
最新 `qpos` 快照，避免完整 RViz 图像链阻塞 1 kHz 仿真。完整
`--headless --rviz` 抓取回归已通过，12 秒保持高度仍为 0.097 m；
`./view_mujoco_camera.zsh` 保留为只检查相机的工具。固定方块完整验收统一使用
`./accept_cube_grasp.zsh`，加 `--rviz` 时会同时显示机械臂、MoveIt、RGB 和
对齐彩色深度视图，原始深度调试视图默认关闭但可手动开启。

MuJoCo→RViz 场景可视化桥已经实现：`Object Meshes` 以 25 Hz 显示三个
原始 OBJ 并持续跟随 MuJoCo 真值；`MuJoCo Physical Collisions` 直接遍历
编译后模型中实际启用接触的 geom；`MoveIt Planning Collisions` 独立显示
规划场景。RViz 默认开启机械臂、物体 mesh 和两个相机面板，默认关闭两套
碰撞层；两套碰撞层打开时地面均不透明。固定方块 mesh 不再受 MoveIt
移除/附着生命周期影响。

下一步最值得做的是把固定真值方块替换为“相机观测得到的方块位姿”。
先保持同一套 MoveIt 抓取执行链不变，从而把感知
误差与运动控制问题分开验收。

日常固定方块验收已经封装为工作区根目录的单命令脚本：

```bash
./accept_cube_grasp.zsh                   # MuJoCo GUI
./accept_cube_grasp.zsh --headless        # 无 GUI
./accept_cube_grasp.zsh --rviz            # MuJoCo GUI + 完整 RViz
./accept_cube_grasp.zsh --headless --rviz # 仅完整 RViz
```

两个参数相互独立，四种组合都会执行抓取。脚本负责启动、就绪检测、成功
字符串与退出状态检查，以及后台进程清理。交互式终端使用 `--rviz` 时，
脚本会在抓取前和成功后各等待一次 Enter，方便检查初始/最终状态和切换三层
可视化；非交互调用会自动跳过等待。

## 2. 项目目标与系统边界

目标是在约 10 平方米区域内，由 Unitree Go2 搭载 Unitree D1-550 机械臂，自动拾取随机散落的 12 件垃圾并投入固定垃圾桶。

系统总体流程：

1. Go2 自主移动到某件垃圾附近；
2. Go2 侧的总流程调用机械臂子系统的 `Pick` 高层接口；
3. 机械臂利用 eye-in-hand RealSense D435i 主动调整视角、精定位并完成抓取和举起；
4. Go2 携带垃圾移动到垃圾桶附近；
5. Go2 侧调用机械臂子系统的 `Place` 高层接口；
6. 机械臂完成投放并收回，Go2 继续处理下一件垃圾。

机械臂子系统并不只是机械臂驱动，它内部包含：相机、感知、主动视角调整、运动规划、夹爪控制和抓取流程管理。Go2 侧不应直接操纵机械臂关节或夹爪。

### 硬件与已知约束

- 移动平台：Unitree Go2；
- 机械臂：Unitree D1-550；
- 相机：RealSense D435i，eye-in-hand 安装；
- 真机部署时，机械臂和 D435i 都连接到 Go2 扩展坞，由机器狗端运行并控制整体流程；
- 夹爪净开口约 6.5 cm；
- 第一版明确规定：执行 `Pick` 或 `Place` 时，Go2 必须站稳并保持不动；
- 机械臂必须自主感知和决定抓取位姿，而不是依赖人工给出精确物体位姿。

### 三类目标物体

1. 黄色立方体：边长 5 cm；
2. 绿色西葫芦：长条形，可能有一定弯曲；
3. 碗：始终开口朝上，碗口直径约 11.5 cm。

## 3. 核心感知思路：两阶段主动感知

已经确定的核心原则是：

> 第一次斜视观测只负责粗定位；机械臂随后把 eye-in-hand 相机移动到目标正上方，第二次俯视观测再完成精确抓取位姿估计。

这是整个抓取方案最关键的简化。不要优先尝试在任意斜视角下直接恢复完整 6D 位姿。固定类别、已知几何且能主动换视角时，俯视后的二维 mask 几何通常已经足够；深度主要用于粗定位和确定抓取高度。

通用流程：

1. Go2 到位并站稳；
2. D435i 获取 RGB-D；
3. 分割目标并获得粗位置；
4. 机械臂将相机移动到目标正上方；
5. 必要时通过图像中心误差继续微调，使目标居中；
6. 根据物体类别运行专用的俯视位姿估计算法；
7. 规划并执行抓取；
8. 验证结果并举起。

## 4. 三类物体的当前抓取方案

### 4.1 立方体

粗定位：从相机中心经过分割 mask 中心发射三维射线，与离地 2.5 cm 的水平面相交，将交点作为立方体中心的近似值。斜视下 mask 中心不等于真实立方体中心，但作为移动到俯视观察位的粗定位已经足够。

俯视精定位：

1. 相机光轴对准 `-world_z`；
2. 重新分割立方体并使其位于图像中心附近；
3. 对 mask 轮廓做四边形拟合或 `minAreaRect`；
4. 从正方形边方向估计 yaw，yaw 只需在模 90°意义下确定；
5. 夹爪闭合方向与立方体的一组边对齐，执行 top-down 抓取。

关键约束：夹爪开口 6.5 cm，立方体边长 5 cm，但面对角线约 7.07 cm，因此不能忽略 yaw 后随意夹取。俯视后估计边方向正是为了解决这个问题。

### 4.2 西葫芦

移动到西葫芦正上方后：

1. 用 HSV/Lab 颜色阈值提取绿色像素，并做简单形态学去噪；
2. 西葫芦近似笔直，可对 mask 像素做 PCA 得到长轴, 然后提取骨架，并仅在骨架中部的一小段估计局部长轴，避免全局 PCA 给出错误抓取方向；
3. approach vector 取向下的地面法向 `-world_z`；
4. closing vector 取水平面内垂直于局部长轴的方向，可由地面法向与长轴叉乘得到；
5. 抓取位置取物体中部附近，抓取高度由深度、地面高度、物体半径和 TCP 偏置共同确定。

注意：物体中心/抓取目标点不是 TCP。TCP 是固定在夹爪上的工具坐标系。

### 4.3 碗

碗始终开口向上，因此先移动到碗正上方，再拟合俯视圆形轮廓：

1. 重新分割碗；
2. 对碗口圆或稳定可见的圆形轮廓做鲁棒圆拟合；
3. 得到圆心和半径；
4. 碗具有旋转对称性，不需要估计 yaw。

但圆心只是定位基准，不一定是最终夹爪中心。由于碗口直径约 11.5 cm，大于夹爪开口 6.5 cm，当前考虑“一指在碗内、一指在碗外”夹住碗沿：

- 在圆周上选择一个碗沿抓取点；
- closing direction 沿该点的径向；
- 夹爪中心对准碗沿，而不是碗心。

这一机械抓取方式需要优先通过简单真机实验验证稳定性。若不可行，应先调整末端执行器或抓取方式，而不是继续堆视觉算法。

## 5. ROS 2 的 high-level 决策

### 5.1 ROS 2 是系统集成骨架

本项目从开发阶段起就基于 ROS 2 组织，因为最终必须部署到真机，并且需要整合 Go2、D1-550、D435i、感知、规划和任务流程。

ROS 2 主要负责：

- 模块通信与任务调度；
- TF 和时间戳管理；
- RViz2 可视化；
- rosbag2 数据录制与复现；
- 对接 MoveIt 2 等规划工具；
- 让仿真与真机共享上层接口。

机械臂的高频伺服、SDK 通信、看门狗和底层安全逻辑仍应留在 D1 驱动/厂商 SDK 层，不应依赖普通 ROS 2 Python 节点实现硬实时控制。

### 5.2 优先复用 ROS 2 生态

优先考虑使用：

- `tf2`；
- RViz2；
- MoveIt 2；
- `robot_state_publisher`；
- rosbag2；
- RealSense 官方 ROS 2 驱动；
- Go2 的 ROS 2 接入。

是否从第一版就实现完整的 `ros2_control` hardware interface 尚未决定，需要先检查 D1 SDK 能力。不要为了形式完整而过早增加复杂度。

### 5.3 MuJoCo 与真机共用上层接口

开发期间必须能连接 MuJoCo 验证算法。架构原则是：

```text
感知/抓取/任务逻辑
        ↓
统一的 ROS 2 接口
        ↓
MuJoCo 驱动 或 D1 真机驱动
```

上层 manipulation 算法不应知道当前连接的是 MuJoCo 还是真机；只替换底层驱动和必要配置。需要特别避免在算法代码中直接调用 D1 SDK 或 MuJoCo API。

仿真与真机可以在传感器噪声、控制频率和安全限制上使用不同参数，但接口语义应保持一致。

### 5.4 Go2 与机械臂子系统的职责边界

Go2 侧负责：

- 自主搜索/导航；
- 判断已接近垃圾或垃圾桶；
- 保证调用机械臂任务前已经站稳；
- 调用机械臂子系统的高层任务接口；
- 根据任务结果决定继续、重试或放弃。

机械臂子系统至少暴露两个长任务接口，倾向使用 ROS 2 Action：

- `Pick`：主动观察 → 精定位 → 规划 → 抓取 → 举起；
- `Place`：到垃圾桶附近后执行放置/投放 → 收回机械臂。

它们应返回执行阶段、成功/失败以及明确的失败原因。具体 Action 字段目前尚未设计，不要现在就锁死。
